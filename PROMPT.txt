我们组做低速无人车的组合导航，每次路测回来，要把车上记下的惯性测量单元数据和卫星定位数据重新融合一遍，看轨迹和误差估计。现在这件事靠一个离线脚本，只能等整段数据拷回来再跑，改一次噪声参数就得从头来，而且路上传回来的数据经常乱序、缺段、重复，脚本遇到就直接崩。我想把它改造成一个常驻后端：车在路上时数据分批推上来，服务边收边算；收完以后还能换一套参数重新融合，两次结果并排比较。

融合对象是捷联惯导的误差状态卡尔曼滤波：名义状态由惯性数据积分得到（位置、速度、姿态），滤波器估计的是它们的误差以及加速度计和陀螺的零偏，卫星定位的位置（可选速度）作为观测。导航在以起点为原点的局部北东地坐标系里进行，重力取常值，地球自转忽略。惯性数据是定频的角增量和速度增量，卫星观测频率低得多，时间戳与惯性数据不对齐。先把几件能手算的事钉住：车静止、传感器无误差时，纯惯导六十秒后的位置漂移应为零；只给北向加速度计加 0.01 m/s² 的常值零偏、不给卫星观测，六十秒后北向位置误差应为 18 m；只给垂向陀螺加 0.01 °/s 的零偏，一百秒后航向偏 1°。滤波器每次观测更新后，对应位置分量的方差不应大于更新前，协方差矩阵任何时刻都要保持对称且半正定。

数据以"一次路测"为单位组织。车端按块推送，每块带序号和时间范围，块可能迟到、重复，也可能某块里夹着比已处理数据更早的记录。无论到达顺序如何，路测收齐后的融合轨迹、零偏估计和协方差，都要和把全部数据按时间排好一次性处理的结果一致（相对误差不超过 1e-9 量级，由你说明取的容差和理由）；重复块只算一次。迟到数据怎么处理由你决定：定期保存滤波器快照、回退到迟到数据之前的快照再重放是一种思路，快照间隔多大、保留多少、是否按内存预算淘汰，都要在文档里说明代价，以及在最坏的迟到情况下重放要花多久。迟到超过你设定的上限时，服务应明确告诉车端这块被拒收以及原因，而不是悄悄吞掉。

融合参数（各项噪声谱密度、初始不确定度、零偏随机游走强度、观测噪声）形成参数集，每个参数集有版本。对一次已收齐的路测，可以指定参数集版本发起重新融合作业，作业异步执行，可查进度、可取消；同一路测、同一参数版本的重复请求直接返回已有结果。两次融合结果能按时间对齐比较，给出位置差的最大值和均方根。服务重启后，正在接收的路测能继续收，已完成的结果都在，跑到一半的作业标记为中断并可重新发起。

请求里出现下列情况要拒绝并指出是哪个字段：惯性采样间隔非正或同一块内时间戳倒退、噪声参数为负、观测时间落在路测时间范围之外、块序号重复但内容不同（要当作冲突报出来，不能按"重复"丢掉）。

测试里我最在意这几件：上面三个手算场景；随机打乱块的到达顺序、混入重复块后与顺序处理一致；协方差对称半正定；观测更新后方差不增；取消作业后状态正确且不留下半截结果；重启后续收。

后端用 Python 3.12 与 FastAPI，数据块、快照和结果存 PostgreSQL 16。代码按职责拆成多个模块：惯导机械编排、误差状态滤波、乱序与重放、参数集版本、作业调度、接口层各管一块，矩阵运算可以用 NumPy。镜像基于 python:3.12-slim，数据库用 postgres:16-alpine，通过 docker compose 编排启动，测试用 pytest 写在仓库里。只需要 HTTP 接口。
